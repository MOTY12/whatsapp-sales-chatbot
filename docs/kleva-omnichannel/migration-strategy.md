# Incremental migration strategy

Apply additive migrations with compatibility flags. Use the existing migration preflight pattern and disposable PostgreSQL fixtures. Never edit historical migrations. Preserve business, user, customer, conversation, message and CRM IDs. Treat credential migration as a separate secure backfill with audited reconciliation.

| Step | Compatibility and data work | Verification and rollback |
| --- | --- | --- |
| 0 · Verify identity | Reproduce HEAD, repair TENANT-002 in its own implementation task, validate permissions, OIDC and legacy behavior before exposing new tenant data. | Lint, build, unit, HTTP, full PostgreSQL/Redis integration and scoped auth proof. Disable new auth via config if rollout fails. |
| 1 · Expand provider schema | Add ChannelConnection, ExternalContactIdentity, receipt/send records and nullable connection/thread/message fields. Add routing constraints in stages. | Fresh/revert/reapply and populated upgrade with invalid references. Older binary still reads legacy fields. |
| 2 · Map WhatsApp history | Backfill only attributable business/number/customer records, preserve provider IDs and history. Quarantine ambiguous links and duplicate open threads for operator review. Encrypt existing secrets and compare ciphertext coverage without displaying them. | Repeat backfill and compare row counts, ID links, tenant mismatches and key coverage. Roll back reads via feature flag while legacy compatibility columns still exist. |
| 3 · Wrap adapter and shadow ingress | Wrap current parsing, challenge and sender functions. Keep legacy processing owner during shadow. Compare canonical event and route outcomes. Shadow writes have separate IDs or no effect. | Golden raw Meta fixtures, schema diff, two-tenant routing, exact signature and duplicate events. Disable shadow by flag. |
| 4 · Cut over per tenant | Enable receipt/outbox and worker processing for controlled tenant cohort. Exactly one processing owner per event. Dedup owner effects, store statuses and preserve conversation ordering. Reconcile early statuses, uncertain sends and queue leases. | Restart and crash drills, provider sandbox traffic, in-flight handoff, closed window, duplicate batches and rollback without duplicate sends. Drain or park in-flight claims before reverting. |
| 5 · Enable shared sales agent | Add knowledge/catalog, playground, inbox/handoff, then enable live grounded replies and qualification by explicit opt-in. Use safety and cost gates. | Evals against active revisions, foreign data rejection, budget and prompt-injection fixtures. Turn off live automation and keep human inbox. |
| 6 · Add providers | One adapter per approved platform behind per-tenant flags, using the same normalized contracts. Link identities only with verified evidence. | Per-provider sandbox and contract tests, status/rate/window/consent tests and failure replay. Disconnect one provider without disrupting others. |
| 7 · Contract after pilot | Retire legacy fallback readers and plaintext fields after reconciliation, restore drill, and compatible rollback window. Preserve historic IDs and read-only mapping. | Forward migration preferred after identity and traffic rollout. Restore encrypted backups with key access and replay validation. |

Run migrations under a dedicated role, verify maintenance locks for legacy column changes, and keep worker deployment behind schema version checks. Preserve operation UUIDs during rollback and queue reconstruction. Redis state can be rebuilt from PostgreSQL. External requests already handed to a provider cannot be recalled by database rollback. Reconcile those attempts before retrying.

## CHANNEL-001 rollout

Apply `AddChannelConnections1760000000006`. Its short-lived PostgreSQL share lock on businesses keeps concurrent legacy writes out of the migration snapshot. The additive table references the original business IDs, uses forced RLS and has no grants for merchant or identity roles. Provision internal runtime table access according to the deployment's existing grant policy. The indexed route key is `(provider, externalAssetId)`. WhatsApp uses WABA ID for the account and Meta `phone_number_id` for the asset. A pending or inactive row reserves its key. An active WhatsApp row requires verification time and account ID. Transfers need a future explicit ownership workflow.

The migration treats a complete saved legacy signup as historical connection evidence. A candidate needs an active business, exact canonical asset ID, unambiguous ownership, WABA ID, connection timestamp and a nonblank credential. It copies metadata only. Competing normalized legacy IDs are skipped and reported with an aggregate warning. Incomplete rows also remain outside the backfill. Re-running the backfill preserves existing connection IDs and status. An imported route still requires agreement with current legacy evidence, so legacy disconnects or rotations cannot leave the previous asset routable through the new resolver. A conflicting legacy write after migration is fenced by the resolver's single-snapshot comparison. When no row exists, fallback requires exactly one active complete legacy mapping.

CHANNEL-001 adds no public route and does not switch existing traffic. Confirm provider ownership and subscriptions during TENANT-004, then compare routes on staging before WHATSAPP-001 adopts them. Live credentials remain in the legacy store until encrypted migration. Rollback drops the new table, ownership trigger and lookup index without touching legacy data. Once later features reference channel IDs, coordinate application rollback and preserve that data before reverting.
