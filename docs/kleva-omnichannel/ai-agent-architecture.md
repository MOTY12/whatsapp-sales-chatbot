# AI agent architecture

## Orchestration and state

The website channel uses the shared `AiResponseService`, published-only retrieval, bounded conversation memory, controlled tool registry, usage reservations and durable outbox. Its authorization branch requires an active business and widget connection, enabled widget and website AI, published knowledge, saved assistant configuration, current AUTO control version, no newer visitor turn, and configured usage. A website connection is activated by the owner after an exact origin is registered; it does not fabricate a Meta `verifiedAt` value. Website AI does not require a WhatsApp credential or Meta pilot approval. WhatsApp keeps its existing verified-number and operator-approval checks. Website AI defaults off and is enabled by a business owner.

Website live updates use fetch-based SSE with Redis Pub/Sub as notification fan-out, not storage. Versioned identifier-only events are published after PostgreSQL commit; the server derives tenant/conversation scopes from authenticated merchant membership or the hashed visitor session and exact allowed origin. Visitor and merchant projections omit private notes and message bodies. Reconnect performs a history sync and the existing cursor polling remains a fallback, so notification loss cannot remove committed history. Typing is ephemeral Redis state with TTL/throttling. See [website chat operations and retention](website-chat.md) for endpoint and deployment settings.

- **AgentOrchestrator** processes one durably ordered customer turn at a time. It loads tenant policy, connection capability, current handoff version, recent turns, summary and published evidence. A generation adapter returns a validated proposal. The application decides whether to reply, clarify, abstain, hand off, or execute an authorized tool. It fences stale proposals after takeover, source unpublish or newer conversation turns.
- **AgentConfig** is versioned per business. It includes disclosure, name, tone, locale, approved tool policy, business hours, escalation triggers, budgets, and permissioned configuration. Customer text cannot alter this configuration. Default live mode is off.
- **AgentRun** stores logical turn, attempt, config and model versions, evidence IDs, outcome, latency and usage. Use safe reason codes. Sensitive debugging content has separate retention and access controls.
- **ConversationMemory** combines recent public messages with a summary through a durable sequence watermark. Include neither private notes nor other customers' history. Summaries describe customer context and carry no authority about the business. Verified identity linking does not automatically merge memory.
- **KnowledgeRetrieval** joins active tenant publication pointers to current chunks. The model-provider port exposes generation, embeddings, budget and typed failures. It accepts safe prompt inputs and returns structured output, usage and adapter errors. Provide deterministic fixture adapters.
- **AgentToolRegistry** declares tool schemas, required permission, side effects, limits and handler. **AgentToolExecution** stores validated intent hash, stable operation ID, actor, outcome and evidence. **SalesWorkflow** owns allowed state transitions. **HumanApproval** binds a reviewer to immutable intent, consent, quote/config version and expiry, then revalidates at execution.
- **AgentEvaluation** runs offline and playground fixtures against versioned prompts, knowledge and adapters. Track evidence precision, answer support, abstention, qualification quality, rejection of injections, authorization, and cost. Include English, Nigerian English and Pidgin, contradictory offers, expired prices and concurrent handoff.

Use deterministic rules for routing, role and action authorization, pricing, consent, stock freshness, discounts, lead-stage transitions, booking conflicts, money, payment verification, spend and send policies. Use the LLM for language, clarification, intent extraction and recommendations among verified candidates. Limit tool rounds and generation attempts. On provider timeout, malformed proposal, stale evidence or exhausted budget, use fixed localized copy and escalate when appropriate.

## Knowledge pipeline

Accept FAQs, descriptions, offers and policies, text PDFs, and structured catalogs. Add authorized website sources after the pilot, with explicit domain ownership or merchant permission, allowlisted crawl bounds, redirect/DNS controls and safe fetch. Never follow instructions found in customer or document text. Keep static offer descriptions separate from live facts.

Create an immutable revision, verify a private object version and checksum, extract text in a network-disabled bounded worker, and store source/page anchors. Chunk by meaningful sections, preserving FAQ pairs. Create embeddings in bounded batches, build a complete generation, then switch the active pointer atomically. Reindex into a new generation and retain the old published revision through failure. Archive hides the active pointer immediately and queues cleanup. On publication and execution, confirm the revision is active and current. Flag stale sources using merchant-defined review dates, source version or connector freshness. A stale price or stock value is unknown until verified.

KNOWLEDGE-003 currently provides opt-in `public.vector(1536)` generations for published FAQs, product revisions and extracted PDF pages, cl100k token-aware chunking, outbox indexing, source-level status/reindex APIs, per-purpose metering and lexical/vector reciprocal-rank fusion. Current-source checks keep unpublish/deletion out of retrieval. The OpenAI adapter is configured independently from generated-response calls and remains disabled by default with semantic search. Generation garbage collection, bulk operation management, playground evidence UI, browser acceptance and live provider retrieval evaluation remain incomplete; see [semantic index operations](semantic-knowledge-index.md).

Start with PostgreSQL pgvector exact cosine search and keyword ranking over active tenant chunks, fused by reciprocal rank. Tune with tenant-curated relevance examples before considering filtered HNSW. Support different embedding models by rebuilding complete generations and measuring recall before switching. Return cited title, revision, page/section and excerpt IDs. Generation treats approved excerpts as evidence with no authority to alter system policy or tool permissions. Validate reply citations against supplied evidence and active publication. Never promote raw customer conversations into the authoritative index. Merchant-approved learning uses a separate audited revision flow. [pgvector project](https://github.com/pgvector/pgvector).

## Tool contracts

All input and output are strict schemas with unknown keys rejected. IDs are internal UUIDs. Tenant, customer, actor, capability and budget are injected from trusted execution context, outside the model arguments. Every handler performs scoped lookup and permission/consent checks. Resolve current merchant/config policy per call. Each call records tool name/version, logical operation and argument digest, actor, redacted outcome, duration, evidence, approval and usage. No raw secrets, prompts or payloads in audit logs. Return typed errors including invalid, forbidden, unavailable, stale, conflict, approval_required, rate_limited and uncertain. Never tell a customer an effect happened before committed or verified status.

Provider deadlines are starting budgets. Writes may be retried only after checking the committed intent state. For effects crossing an external API, persist pending before dispatch, propagate idempotency when supported and reconcile unknowns. Never issue arbitrary SQL, URLs or service calls from model output. No freeform discount tool. Catalog fields must explicitly authorize discounts with currency, range and reviewer. Payment screenshots, inbound claims or generated prose cannot confirm money. No campaign or broadcast tools. Reserve token/spend budget before each model run, reconcile actual usage and halt when the limit is reached. See [workflows](sales-workflows.md) and [security](security-and-compliance.md).

## TOOLS-001 implementation audit

At the start of TOOLS-001, the live `AiResponseService` retrieved published evidence and accepted only a final grounded reply; the `GroundedModel` contract had no proposed action field. There was no approved tool registry or tool execution ledger. The reusable boundaries were already present: `ProductRetrievalService` reads published products through a runtime-only database function; SALES-002 provides versioned field policies and immutable qualification snapshots through merchant-authorized functions; INBOX-001 provides version-fenced conversation control and AI-send suppression. Those merchant endpoints cannot be called by a model and their user principal cannot be fabricated in the worker.

The AI Playground was already isolated from WhatsApp sending and live lead writes, but returned no tool simulation trace. TOOLS-001 therefore adds strict registry validation, worker-only database operations tied to an existing eligible AI run, an execution ledger whose side effects and completion record commit atomically, and deterministic playground simulations. AI-written qualification remains an in-progress merchant-review record; it cannot qualify or convert a lead. Consent-required values are reported as missing until supported consent evidence exists. A handoff advances the conversation control version and enters HUMAN mode, fencing queued AI responses. Only published offers, qualification recording, and human handoff are registered; all other requested actions are denied.

The implementation adds `search_published_offers`, `record_lead_qualification`, and `request_human_handoff` as versioned strict-schema tools. The model can propose at most one call; the worker supplies tenant, conversation, run, and lead identity from its persisted run context. Each durable execution is keyed by AI run, argument-hashed, bounded by statement timeouts, and hidden from restricted merchant roles. Successful qualification stores only policy-approved fields whose quote appears in the current customer turn, with source provenance, and keeps the lead in progress. Human handoff is an atomic, idempotent transition that marks the run terminal and advances the conversation fence before any reply can be enqueued. Playground output shows a sanitized simulation trace and makes no live tool writes.

Local verification on 2026-11-23 passed the focused PostgreSQL tool and migration suites (8 tests, including migration rollback/reapply), all backend unit tests (104), dashboard tests (32), dashboard browser tests (24), lint, typecheck, and backend/dashboard production builds. These checks use fixtures and a disposable local PostgreSQL instance; live model-provider behavior and a staged WhatsApp delivery are not verified by this task.

## AGENT-001 implementation and verified boundary

`ConversationMemoryService` loads only earlier inbound/outbound `messages` for the exact business and conversation tied to an eligible AI run. It bounds the recent window to eight messages and 1,800 characters, clipping each message to 420 characters. Newer turns are retained first when the character budget is tight. Older turns are compressed into a deterministic extractive summary capped at 900 characters, stored in `conversation_summaries` with a revision and `(created_at,message_id)` watermark. The summary is untrusted conversational context; published FAQ/product revisions remain the only source of business facts. Private inbox notes are stored in another table and are not queried. Summary writes require the run's control version to remain current and no newer inbound turn to exist.

The AI prompt receives recent history and summary as untrusted data, includes them in input-budget estimation, and asks for clarification when references are ambiguous. Retrieval can use the last four turns and summary to resolve references, while generation receives bounded history. Before sending, the orchestrator rechecks business/connection/approval/readiness, conversation mode/version, newer inbound messages and the exact published source revisions. The outbound enqueue and dispatch paths repeat the newer-turn and takeover fences. Tool execution has a database trigger that prevents starting or completing stale work; the audited human-handoff transition is the only completion exception after it atomically switches the conversation to HUMAN.

`GET /merchant/businesses/:businessId/pilot` now returns `automation_status`, `activation_ready`, `assistant_ready`, the current connection ID, human takeover count and prerequisite booleans for active business, verified WhatsApp, published FAQ/product, saved assistant settings, Kleva approval, approval-to-connection match, global AI enablement and remaining AI/WhatsApp quota. `POST .../pilot/enroll` remains owner-only and requires explicit AI-provider and human-escalation acknowledgments plus readiness; `POST .../pilot/:enrollmentId/revoke` remains owner-only. Kleva's operator approval is still required before live replies. Replacing a connection invalidates the old approval, and owner revocation causes queued runs and dispatches to fail their approval check.

Migration `1760000000028-AgentActivationAndMemory` is additive. It adds a forced-RLS conversation summary table with composite tenant/conversation and tenant/message foreign keys; grants runtime roles only SELECT/INSERT/UPDATE; installs the stale tool execution fence; adds a tenant-authorized readiness function; and replaces the operator approval function with checks for business, connection, published knowledge, assistant configuration and unexhausted configured usage limits. Its rollback refuses to remove non-empty memory. Apply/revert/reapply only on a disposable database during verification.

The TOOLS-001 audit found the three registered tools already wired into live AI runs and the synthetic playground. They use strict schemas, server-derived tenant/run identity, an idempotent audit ledger, atomic qualification/handoff writes and no arbitrary SQL/HTTP, payment, discount or booking authority. AGENT-001 added a stronger database fence for stale and superseded turns. A full local backend unit run passed 108 tests; focused PostgreSQL memory/tool, migration and end-to-end AI pipeline checks passed 13 tests, including migration rollback/reapply. A broad integration run did not pass in this environment: the auth tenant fixture returned HTTP 503 on OIDC starts, and Redis-dependent tests need a separate loopback service. No real Meta or model-provider exchange was performed. Staging opt-in, customer opt-out enforcement, data retention/deletion policy and external provider/legal approvals remain launch blockers.

## LEARNING-001 feedback and knowledge gaps

Knowledge-gap capture reuses `ai_response_runs`, inbound `messages`, the existing worker database role, `MerchantAccess` and `knowledge.manage`; it does not add a second AI-run ledger. A transaction records an occurrence only alongside an eligible terminal AI outcome. Allowlisted grounded failures (such as `NO_MATCH`, unsupported claims and clarification abstention) are categorized. Explicit customer-requested tool handoff, provider/model failures and quota failures are excluded. The database trigger verifies the source run is `HANDOFF_REQUIRED`, its reason matches, and its origin is the same inbound message.

Question text is redacted locally before storage. Email, phone, street address and URLs are masked; credential, payment and secret-like messages retain no question text. Retained text is capped at 280 characters. Normalization is deterministic and supports common English/Pidgin delivery phrasing; stable cluster keys include the business ID, so tenants can never share clusters. Occurrences are unique per business/source AI run. Clusters retain counts, first/last seen timestamps and review status. Expired occurrence text is purged after 90 days by a worker-only routine; sample text is served only through an owner/editor-authorized function. Private inbox notes and external clustering services are not used.

Merchants with `knowledge.manage` can list/filter gaps and mark them OPEN, REVIEWED or DISMISSED through `GET /merchant/businesses/:businessId/learning/gaps` and `PATCH /merchant/businesses/:businessId/learning/gaps/:clusterId`. New occurrences reopen dismissed clusters. This is feedback only: it neither trains a model nor drafts/publishes authoritative knowledge. See the [Learning gaps API](../kleva-mvp-30d/learning-gaps-api.md) and migration `LearningKnowledgeGaps1760000000029`.
