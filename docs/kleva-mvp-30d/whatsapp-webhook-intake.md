# WhatsApp webhook intake

POST /webhooks/whatsapp reads an uncompressed body up to 256 KiB. It verifies the exact bytes using Meta's SHA-256 HMAC header before decoding UTF-8 or parsing JSON. Missing or invalid signature evidence returns 403. A valid signature on invalid JSON or an invalid envelope returns 400. The subscription challenge remains on GET.

Each supported event must resolve by phone number ID to an active channel connection, and the envelope's WABA ID must match the connection's provider account. Unroutable, inactive, disconnected, conflicting or unsupported events are discarded without storing the payload. Legacy mappings without a connection row are deliberately ineligible. Meta receives 200 for an authenticated valid envelope after all eligible events commit, including envelopes with no eligible events. A failed transaction returns 503 for retry. Redis availability is independent of the HTTP response.

Receipts use a UUID shared with the outbox operation. The uniqueness key is provider, connection and event key. A message key uses the provider message ID. A delivery key uses the provider message ID and status, so repeated instances of one state collapse and distinct states survive. The first accepted payload wins. Each receipt stores tenant and connection IDs, event type, receive time, handoff time and the fields needed downstream. Text events retain sender ID and text. No raw request envelope, contact profile, credential, or signature is stored. Composite foreign keys enforce receipt, connection and outbox tenant agreement.

Outbox status, attempts, lease and safe last error are the authoritative retry metadata. The worker locks the receipt and its channel connection, checks that the receipt's business matches both the connection and outbox, and processes the event in the same transaction as outbox completion. Inbound processing rechecks that the connection is active and verified. Inactive connections are marked as skipped and do not create customer traffic.

For a text message, processing looks up or creates the customer within the receipt's business, serializes work for that sender and business, reuses the latest tenant conversation or creates one, and inserts the inbound message with the provider message ID. The message unique index and tenant foreign keys are the final deduplication and isolation checks. Conversation and customer writes, message creation, receipt outcome and outbox completion commit or roll back together. Replays therefore cannot leave partial customer or conversation writes.

Owner classification requires an active `business_members` row with role `owner` and the exact verified WhatsApp ID for this business. Matching a legacy `users.whatsappId` alone does not grant owner status. Legacy onboarding sessions are classified separately. Both classifications create a `PENDING` row in `whatsapp_response_intents`; the worker does not call the assistant or send a network request in its database transaction. WHATSAPP-003 must consume these response intents through durable outbound delivery. Customer messages are marked ready for later inbox/AI work; this phase does not generate an AI answer or send a new-lead alert.

Delivery status receipts update only an existing outbound message with the same provider ID and business. Status ordering will not downgrade `read`, `delivered`, or `failed` records. Unmatched receipts remain in `webhook_receipts` with outcome `unmatched_delivery`; no synthetic outbound message is created. WHATSAPP-003 owns complete outbound retry/reconciliation behavior.

`AddWebhookReceipts1760000000008` adds durable intake. `ProcessWhatsAppReceipts1760000000009` adds processing timestamps/outcomes, composite tenant keys and the pending response-intent table. The runtime worker role needs SELECT/INSERT/UPDATE on receipts, normal customer/conversation/message permissions, and SELECT/INSERT/UPDATE on `whatsapp_response_intents`. Keep receipt data private. Retain receipts and outbox rows until downstream response delivery, the provider retry window and the approved retention window have elapsed. No automated purge runs yet. Removing receipts also removes deduplication evidence. Migration rollback refuses when response-intent history exists; the earlier receipt migration also refuses while receipts exist.
